# Independent repair gate

`verifier/verification-contract.json` is protected acceptance policy. Pin its SHA256 when presenter repair authority is granted. The repair task cannot edit it. `scripts/gate_repair.py --mode contract` prints the digest and explicitly reports runtime not run.

## Integration

`RepairExecutor(runtime).start(mission, on_event)` blocks while a real isolated Codex process runs; call from the controller's background job. `status(jobId)`, `cancel(jobId)` and `collect_artifacts(jobId)` remain available. Runtime configuration:

- `image`: prebuilt image with a pinned Codex CLI and required runtime tools; record its measured CLI version and actual image ID in the repair boundary artifact and job evidence.
- `network`: externally provisioned broker-only network; `networkVerified: true` only after a repair-specific measured containment gate. `boundaryEvidencePath` must identify a JSON artifact with a matching actual image ID and network, positive model relay reachability, explicit denial of payment application, effect store, controller, verifier, unrelated host paths, metadata, platform, external and Docker socket access, and measured writes confined to `/workspace/payment_app`, `/home/repair`, and `/tmp`. The evidence must be from the last hour. OpenShell additionally needs measured policy and Landlock coverage. A worker image probe cannot authorize repair.
- Each Docker repair job also checks the measured internal network and relay container identity, its read-only Caddy configuration digest, effective denial of the bridge gateway API, and reachability of the exact model relay path before launching Codex.
- Optional `dockerHost`, `memory` (default 768m), `timeoutSeconds` (capped at 600).

Mission keys are the frozen `contracts/v1.md` keys. `expiresAt` is a Unix timestamp. `modelBaseUrl` points at the task broker's OpenAI-compatible `/model/v1` base; `modelToken` is a short task lease, never the Azure key. `artifactDir` must be writable by the trusted supervisor. The runtime gets a new HOME/CODEX_HOME, task-only model config, no developer login/plugins/MCP, readonly base and writable `payment_app/` only. It has no Docker socket or trusted store mount. Agent JSONL is untrusted evidence and never certification. `candidate` means patch collected, not verified.

`verifier.runner.verify(config)` uses `repoPath`, full immutable `baseCommit`, `patchPath`, `artifactDir`, `verificationContractDigest`, optional expected `artifactDigest`, and `applicationImage`/`trustedImage`. Both images need Python, FastAPI and Uvicorn; the application image also needs its locked runtime dependencies. Images must already exist locally. Optional `dockerHost`/`supervisorHost` support a trusted supervisor setup; Docker bind source paths must exist on the daemon host. Execute on the Azure host by preference. A remote daemon alone does not transfer source or tunnel loopback ports.

Verifier requires the separately measured, fixed `vs-verify-internal` bridge with an effective host gateway deny rule. It creates fresh application and trusted ledger containers per control on that bridge, without published host ports. The trusted supervisor sends HTTP probes through Docker exec inside the ledger container. Candidate application source is readonly and separately mounted from protected acceptance code and the immutable original store. A distinct trusted service owns the DB on tmpfs. The candidate gets only an environment-scoped service token. The supervisor keeps a separate random admin capability and reads actual ledger state. All containers run UID65532, readonly root, dropped capabilities, no privilege escalation, bounded CPU/memory/processes, and no Docker socket.

Acceptance runs original and UI-only controls first; each must reproduce an unauthorized ledger entry with an unused, valid approval/current revisions/active attempt and compensation disabled. Candidate tests reject beneficiary, amount and currency mismatches, require no effect and no approval consumption, then execute a fresh legitimate approval and an identical retry with one ledger entry. Infrastructure failure reports `blocked`; API errors cannot count as prevention. Exact patch SHA and contract SHA are returned with per-control JSON ledger evidence and container logs.

Before claiming `outerContainment=true`, the verifier also exercises the trusted service over HTTP in a fresh isolated Docker network. Named proofs cover environment, workspace and mission scope; current record revision; active attempt; approval expiry and revocation; and competing operations with one atomic ledger effect. The `outerControls.coverage` map remains `unverified` for any missing or failed proof, and the aggregate verification stays held. The candidate runs in the isolated verifier even when conservative source review rejects it, so a UI-only negative control can still show its actual unauthorized ledger effect. Source review rejects changes outside the approval expression and probes inside it; this narrow review and finite runtime tests do not establish arbitrary patch correctness.

## Remaining runtime prerequisites

A repair-specific Docker boundary gate has passed on the Azure host with a pinned Codex 0.156.0 image, but no Codex source repair or isolated verifier acceptance has run yet. The gate must be fresh for each repair job. The UI-only fixture changes the displayed portal while leaving the API defect intact; never replace it with a generated correct patch. The verifier must test the runtime agent's exact collected candidate.

Run local security unit checks with `.venv/bin/python -m pytest tests/test_repair.py -q`. Run actual gates with `python scripts/gate_repair.py --mode repair|verify --config /private/config.json --output artifacts/result.json`. Keep lease-bearing configuration private; it is not an export artifact.
